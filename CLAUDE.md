## What this project is

**Generate TypeScript SQL parsers we can use in our own projects**, built from open, split **ANTLR4 grammars (`.g4`)** that we fork or hand-author and run through the **antlr4ng** toolchain. Two kinds of target:
- **Fork-and-clean** — dialects with a good existing `.g4` we fork and conformance-validate: **Databricks** (from apache/spark), **T-SQL** and **Snowflake** (from grammars-v4 — the Snowflake one was long assumed not to exist; it does, and is actively maintained — corrected 2026-06-10), **BigQuery** (from `bytebase/parser` `googlesql/`, BSD-3 — corrected 2026-06-13; the earlier "no open grammar" claim was wrong, mirroring the Snowflake correction), and **Redshift** (forked from **Bytebase's Postgres-derived Redshift grammar**, BSD-3, vendored at `grammars/redshift/` — **corrected 2026-06-28**: Redshift was forked and built like the others, *not* hand-authored; the earlier "no authoritative open grammar → hand-author" framing was wrong, the same kind of miss as Snowflake and BigQuery).
- **Fork-of-our-own-fork (added 2026-07-02):** **PostgreSQL** (from `bytebase/parser` `postgresql/`, BSD-3, vendored at `grammars/postgres/` — the same upstream repo/commit as the BigQuery and Redshift forks; our Redshift grammar is itself Bytebase's fork of it) and **DuckDB** (forked from **this repo's own `grammars/postgres/` pair** — DuckDB has no open ANTLR grammar anywhere; its real parser is a Bison fork of PostgreSQL's, so the lineage mirrors reality). The roster is download-driven: these two take dbt-adapter coverage from ~70% to ~85–90% of downloads/mo (numbers in PLAN.md Scope); trino shipped as dialect eight; ClickHouse is the official next candidate, parked by decision 2026-07-03 (downloads part-botted, real ~1.2M/mo — research done, see PLAN.md Scope).
- **First-party fork (added 2026-07-02):** **Trino** — the ONLY dialect whose vendor ships its real parser's ANTLR grammar: grammars/trino/ is trinodb/trino's `SqlBase.g4` (Apache-2.0, pinned release 482) **mechanically split** into this repo's lexer+parser pair (named punctuation tokens, the one Java `isKeyword()` predicate ported to TS, a batch `root` entry added — the whole delta is listed in the grammar headers). Upstream parity is therefore BY CONSTRUCTION — Niclas's fork-vs-official verification mandate is satisfied maximally (no fork drift can exist; on new Trino releases, diff upstream's SqlBase.g4 and re-split/backport). One trino dialect covers dbt-trino AND dbt-athena (Athena engine v3 routes queries/DML to Trino; its Hive side is object DDL, out of scope).
- **Hand-author** — **none.** All eight dialects had a forkable open grammar (DuckDB's being our own postgres pair, Trino's being first-party); nothing was hand-authored from scratch. (Historical: Redshift was the original motivation precisely because an open grammar was assumed not to exist — that assumption proved wrong.)

**The primary deliverable is the generated TypeScript parsers** — a `parse(sql, dialect)` library we consume in our own projects, TS-native with no Python or Java at runtime. The `.g4` grammars are the *means*: forking or hand-authoring them is how we build and maintain those parsers, and we optimize for a working parser over grammar elegance. The grammars are a useful by-product — for the warehouse dialects an open spec that doesn't exist today, and where we improve a grammars-v4 grammar we contribute the fix back upstream — but they are not the main delivery.

**Primary usage — this exists to power editor/IDE features (decided 2026-06-13).** The "own projects" that consume it are first and foremost **language tooling**: an **LSP** (diagnostics, hover types, go-to-definition, completion, document symbols) and the **SQL debugger**, both in the sibling `dbt-studio-vscode` extension. So the semantic layer (`scope → qualify → infer → lineage → symbols`) is **central, not a Databricks-only add-on**, and editor-shaped requirements are first-class design drivers — judge designs by "does this serve an LSP/editor consumer": **positional parse diagnostics** (line/column for squiggles, not a bare error count — issue #6), **small per-dialect load** (an extension bundles one dialect, not all eight — issue #8), and stable, immutable analysis results that survive incremental edits. Non-editor / batch programmatic use is supported but secondary; when a design choice trades off, favor the editor/LSP consumer.

**The foundation this mandate REQUIRES — Niclas identified this gap 2026-06-28; BUILT 2026-06-29.** Editor features run on *incomplete, changing, usually-invalid* input (the user is mid-keystroke), so the front end must be a **living-document model**, not a one-shot batch transform: (a) a **first-class, always-available token stream** — every token + exact span + kind, surfaced as an artifact (NOT ANTLR's internal `CommonTokenStream`), and (b) an **error-tolerant parse** that always yields a usable tree on broken / mid-edit text. The interactive editor features — **completion**, **semantic tokens** (semantic highlighting), **signature help** — *live* in the broken-input world and **cannot** be built on a "parse must succeed first" front end. **Current state — built:** `parse()` surfaces a first-class `Token[]` (span + role + channel) and a standalone total `tokenize()`; `lower()` is total (never throws on broken/partial input, all eight dialects); a `SqlDocument` model — immutable, position-addressable, with an O(log n) `LineIndex` — caches `parse → resolveScopes` plus lazy schema analysis; and the LSP serves diagnostics/hover/definition/symbols **plus completion (an owned ATN candidate walk over the grammar's ATN — no antlr4-c3 dependency), semantic tokens, and signature help** from one cached `SqlDocument` per open file, through the public API surface only (the seam to split the LSP into its own repo later). The semantic layer was already editor-shaped; the lexer/parser front end now matches it. **Guardrail (still binding): a green acceptance suite over valid-parse features is NOT proof the editor mandate is served** — judge any editor-facing work against the broken-input foundation, and surface a foundation gap at *design* time, not after building the convenient subset. Reference shape: lossless, error-tolerant syntax trees (tree-sitter, Roslyn, rust-analyzer, the TS compiler).

**The parser is syntax only** — it produces a parse tree. On top of it, for Databricks, we *are* building a **semantic layer** (name resolution = scope, plus schema-fed qualify) because the consumers (editor support, the SQL debugger) need it — Nicke directed this 2026-06-06. **Out — actually Nicke-cleared:** SQL transpilation (Nicke: "i dont care at all about the transpile", 2026-06-06); and **object DDL** — CREATE/ALTER/DROP-style object management (UC object DDL, column MASK/ROW FILTER, Python UDF bodies) — "what we don't do is regular DDL" (Nicke 2026-06-10, refining the broader same-day clearance). **Open, likely future scope (NOT Out):** the operational non-SELECT statements a data engineer runs outside dbt — COPY INTO, Delta maintenance (OPTIMIZE/VACUUM/RESTORE/…), GRANT, UPDATE/DELETE/MERGE modelling depth (Nicke 2026-06-10: "might become in scope … we do it occasionally"). Both sets are pinned at their current support level in `tests/databricks.doc-coverage.test.ts`. **NOT cleared — open, do NOT treat as Out:** **type inference** and **column lineage**. These were carried over from the origin session's "syntax only — no semantic analyzer" framing (which also listed scope resolution + function signatures); Nicke overrode that framing on 2026-06-06 by directing the scope + qualify semantic layer, and never separately cleared type inference or lineage. A prior edit wrongly stamped them "Nicke-cleared" — that was the assistant's assumption, not Nicke's decision. Type info is in fact needed to finish schema-fed validation (e.g. struct-field existence — see [docs/PLAN.md](docs/PLAN.md) Open Gaps); lineage was only ever noted "revisit later" (deferred, rides on qualify), not cut. **Expression modelling** (`a+b`, CASE, calls, aggregates, window/`OVER`, `GROUP BY`/`HAVING`, predicates, lambdas, subscript, the `date_add`/`CURRENT_*` special forms) — **built 2026-06-06**, **corpus-complete: every expr node in all 1558 models lowers to a typed `Expr` — 0 `other`, gated by `tests/corpus/databricks.oatly.test.ts`**. GROUP BY captures every key (incl. inside ROLLUP/CUBE/GROUPING SETS); qualified `t.*` expands only its source; `aggregate` uses a comprehensive Spark aggregate-name set. Was never a descoping.

- **Living-document front end shipped — the editor-mandate foundation is built, the front end is no longer batch-shaped.** The lexer/parser front end now works on incomplete, changing, usually-invalid input: (a) the **token stream is a first-class artifact** — `parse(sql, dialect)` returns `tokens: Token[]` (every token + exact span + role + channel), and a standalone `tokenize(sql, dialect)` exists (`src/token/`); (b) **`lower()` is total** — it never throws on broken/partial input (broken text yields a flagged `query` IR), and statement-level error containment is verified (one broken statement doesn't truncate the token stream or smear diagnostics). ## Locked decisions (don't relitigate without a new reason)

- **Format:** ANTLR4, **split** grammars per dialect — a `lexer grammar <Dialect>Lexer` + a `parser grammar <Dialect>Parser`. Split is required for lexer **modes** (dollar-quoting, embedded JS/Python UDF bodies) and avoids ANTLR's anonymous `T__n` tokens.
- **TS generation:** ANTLR4 TypeScript target + the **antlr4ng** runtime (actively maintained by Mike Lischke; ~9–35% faster than the older, semi-abandoned antlr4ts). **Verified 2026-06-06** on both Databricks and T-SQL: the pure-TS **`antlr-ng` CLI works — no Java/jar needed**. Command: `npx antlr-ng -D language=TypeScript -o src/generated/<dialect> grammars/<dialect>/*.g4` — antlr-ng **defaults to a Java target**, so `-D language=TypeScript` is required. Versions: antlr-ng 1.0.10, antlr4ng 3.0.16. Generated `.ts` uses `.js` ESM imports and runs under vitest with `moduleResolution: Bundler`. (Jar fallback `antlr-4.13.x-complete.jar -Dlanguage=TypeScript` no longer needed.)
- **Build / typecheck compiler:** **TS7 native (`tsgo`, `@typescript/native-preview`)** — adopted 2026-06-06 to experiment ahead of GA. Measured ~2.2× faster than TS6 `tsc` on our generated code (1.8s vs 4.0s; gap widens as dialects are added). `tsc` (TS 6.0.3) stays installed as fallback. `npm run typecheck` runs `tsgo`. **Revisit at packaging:** validate `.d.ts` emit from `tsgo` before shipping — `.ts→.d.ts` is at parity in the 7.0 beta but has tracked intentional diffs (typescript-go#989); fall back to `tsc` for the declaration step only if its output differs.
- **Architecture:** **no shared "core" grammar and no inheritance.** "Core SQL" is a concept (dialects share an ANSI-ish ancestry), not an artifact we build — and ANTLR `import` doesn't compose cleanly anyway. Each dialect is a **standalone pair of split `.g4` files**, forked from its best starting point and edited in place (how dbt/Calcite/everyone does it):
  - **Databricks** ← fork **apache/spark's `SqlBaseLexer.g4`/`SqlBaseParser.g4`** (vendored at `vendor/spark/`), renamed to `DatabricksLexer`/`DatabricksParser`. **Switched 2026-06-06** from grammars-v4's `sql/databricks`: that grammar was light (~30 KB) and incomplete; Spark's is the complete, authoritative grammar (Databricks SQL = Spark SQL) at the cost of a one-time port of its embedded Java `@members`/actions to TypeScript. The port: `getText()`→`this.text`, `_input`→`this.inputStream` (LA returns a char code), `Deque<String>`→`string[]`, every action/predicate prefixed with `this.`, and a `@header` import so the parser's `complexDataType` action can cast the token source to the lexer. Spark relies on a runtime `UpperCaseCharStream` for case-insensitive keywords, which we don't have — replaced with ANTLR's `options { caseInsensitive = true; }` on the lexer. Entry rule is the grammar-local `multiStatement` (a `;`-separated batch of statements and/or BEGIN…END compounds + EOF — added to close issue #1, parity with the other dialects' batch-level entries), not Spark's single-statement `singleStatement` nor the old `databricks_file`.
  - **T-SQL** ← fork grammars-v4's `sql/tsql` (`TSqlLexer.g4`/`TSqlParser.g4`, mature, ~200 KB parser).
  - **Snowflake** ← fork grammars-v4's `sql/snowflake` (`SnowflakeLexer.g4`/`SnowflakeParser.g4`, ~190 KB split pair, maintained by its original author + Bytebase since 2022). **Corrected 2026-06-10:** this repo's earlier claim that no grammars-v4 Snowflake grammar exists was wrong — assessed against the official docs, the grammar earned a fork the same way `sql/tsql` did (no embedded actions, `caseInsensitive` lexer, generated TS first try); the gaps it did have (window frames commented out, star modifiers, MATCH_RECOGNIZE stub, …) were fixed in our fork.
  - **BigQuery** ← fork **`bytebase/parser` `googlesql/`** (`GoogleSQLLexer.g4`/`GoogleSQLParser.g4`, BSD-3, vendored at `grammars/bigquery/`). **Corrected 2026-06-13:** the earlier "no open grammar exists" claim was wrong (same kind of miss as Snowflake). The only work to make it generate as TS was porting the Go-target embedded code (error actions + `localctx`/`:=` predicates) to the antlr4ng API; `caseInsensitive` lexer, generated TS first try. Entry rule is `root` (`stmts EOF`).
  - **Redshift** ← fork **Bytebase's Postgres-derived Redshift grammar** (`bytebase/parser` `redshift/`, BSD-3, vendored at `grammars/redshift/`; TVL PostgreSQL lineage). **Corrected 2026-06-28:** forked like the others, not hand-authored.
  - **PostgreSQL** ← fork **`bytebase/parser` `postgresql/`** (`PostgresLexer.g4`/`PostgresParser.g4`, BSD-3, vendored at `grammars/postgres/`, same pinned commit as the BigQuery/Redshift forks, PG18 keywords). The Redshift port recipe applied: lexer base inlined to `@members`, parser superClass + `ParseRoutineBody` dropped, the `PostgreSQLKeywords.g4` import inlined. Entry rule `root` (`stmtblock EOF`).
  - **DuckDB** ← fork **this repo's own `grammars/postgres/` pair** (renamed `DuckdbLexer`/`DuckdbParser`) — no open ANTLR DuckDB grammar exists (its real parser is a Bison fork of PostgreSQL's; a PEG rewrite is in progress upstream), so the fork lineage mirrors DuckDB's own. Entry rule `root`.
- **Validation:** a conformance harness that parses a per-dialect **known-good corpus** (our own compiled SQL, plus grammars-v4 `examples/` only where they're substantive — they were dropped for Databricks as near-empty stubs) and requires the generated parser to parse it all with **zero syntax errors**. For Databricks the corpus is the real Oatly compiled-dbt SQL (`harness/local/databricks`). No Python in the dev/CI loop, and no sqlglot/oracle cross-check (dropped 2026-06-06). Harness shape mirrors `dbt-studio-vscode/experiments/native-sql-parser-v7/harness`.
- **Dialect order (reordered 2026-06-06; Snowflake pulled forward 2026-06-10; BigQuery pulled forward 2026-06-13; PostgreSQL + DuckDB appended 2026-07-02):** **Databricks** (≈ Spark SQL → forked apache/spark's `SqlBase*.g4`, fastest to first green: 100% on the Oatly corpus) → **T-SQL** (fork grammars-v4's mature `sql/tsql`) → **Snowflake** (fork grammars-v4's `sql/snowflake`) → **BigQuery** (fork `bytebase/parser` `googlesql/` — pulled ahead of Redshift once that fork base proved viable, same as Snowflake) → **Redshift** (fork `bytebase/parser` `redshift/`) → **PostgreSQL** (fork `bytebase/parser` `postgresql/` — the cheapest add ever: the fork base is the repo we'd forked twice and the port recipe was already executed for Redshift) → **DuckDB** (fork our own postgres pair, immediately after so the Postgres grammar knowledge stayed hot) → **Trino** (split the FIRST-PARTY trinodb SqlBase.g4 directly — covers dbt-trino + dbt-athena). Roster driven by dbt-adapter downloads (PLAN.md Scope). **Trino fork requirement (Niclas 2026-07-02) — EXECUTED same day, maximally:** the rule-by-rule diff of the Bytebase fork against the first-party `SqlBase.g4` @482 found 22 missing productions + 67 drifted rules, so the Bytebase fork was DROPPED as grammar base — grammars/trino/ is the official grammar itself, mechanically split, making upstream parity by-construction. Standing rule: on new Trino releases, diff upstream’s `core/trino-grammar/…/sql/SqlBase.g4` against ours and re-apply the (tiny, header-documented) split delta. Bytebase’s `trino/examples` stays as the vendor gate corpus.

## Sources of truth, per dialect

- **Authoritative syntax:** the dialect vendor's official SQL manual. Always wins.
- **Per-dialect deltas:** sqlglot's dialect files (`databricks.py`, `tsql.py`, `snowflake.py`, `bigquery.py`, `redshift.py`, `postgres.py`, `duckdb.py`) — the curated "what's different from base SQL." Read as a reference only (we don't run sqlglot or use it as an oracle).
- **Vocabulary / reserved-word checklist:** dbt's generated lexer token lists in `dbt-labs/dbt-core` → `crates/dbt-sql/dbt-lexer-*/.../*Lexer.tokens`.
- **Reference / fork-base grammars** (`antlr/grammars-v4`, BSD/MIT — forkable): `sql/tsql` (mature, split — the **fork base for T-SQL**), `sql/databricks` (light, split — **cross-reference** for Databricks), plus `sql/snowflake`, `sql/trino` to crib structure. No BigQuery, Redshift or DuckDB there — the Bytebase monorepo (**`bytebase/parser`**, BSD-3) is the fork base for **BigQuery** (`googlesql/`), **Redshift** (`redshift/`) and **PostgreSQL** (`postgresql/`); **DuckDB** forks this repo's own postgres pair (no open ANTLR DuckDB grammar exists anywhere; DuckDB ground truth is duckdb.org/docs/current + its libpg_query-derived Bison grammar in `duckdb/duckdb third_party/libpg_query`, read-only reference).
- **BigQuery ground truth:** Google's **ZetaSQL / GoogleSQL** — the syntax *spec* is now `google/googlesql` `googlesql/parser/googlesql.tm` (a Textmapper grammar; the old C++ Bison `.y` was removed) — read it for exact productions, don't port it wholesale; and the **conformance corpus**: the 377 `googlesql/analyzer/testdata/*.test` golden files drive the two-sided `tests/corpus/bigquery.analyzer.test.ts` + `tests/corpus/bigquery.parser.test.ts` gates (positives must parse, syntax-error negatives must be rejected). The grammar we actually fork is Bytebase's ANTLR port of GoogleSQL, extended toward `googlesql.tm`, not ZetaSQL itself.

## Code map — the pipeline

`parse → lower → resolveScopes → qualify → infer / lineage / symbols`. Only the first two stages are per-dialect; everything after operates on the shared IR and runs unchanged on every dialect.

```
grammars/<dialect>/        split .g4 pair — the hand-maintained source
src/generated/<dialect>/   antlr-ng output (gitignored build product; never hand-edit)
src/<dialect>/parse.ts     parse wrapper: two-stage SLL→LL with BailErrorStrategy, returns CST + error count + positioned diagnostics + the token list
src/<dialect>/lower.ts     CST → IR; the only place that knows the dialect's parse-tree shape. Total — never throws, even on broken/partial input (a flagged `query` IR comes back). Freezes the IR (freezeIR) before returning — the IR is immutable after lower(); no pass writes back
src/ir/freeze.ts           deep-freeze of the IR (skips the foreign antlr `cst`/`aliasCst` back-refs), called at the end of every dialect's lower()
src/ir/ir.ts               dialect-neutral IR (QueryExpr/SelectExpr/SetOpExpr/PipeExpr/Source/Expr…; PipeExpr = base + ordered PipeStage[]; GraphTableSource for GQL); every node keeps a `cst` back-ref for source spans, and `Projection.aliasCst` the alias identifier's own span (all eight dialects — the Anvil per-part cursor surface)
src/token/                 the first-class token stream — token.ts (neutral Token + TokenRole), classify.ts (shared role classifier + per-dialect overrides), map.ts (CST/lexer token → Token + exact span + channel), tokenize.ts (standalone lexer-only tokenize(sql,dialect)). Always available, even when the parse fails
src/minijinja/                 the additive jinja-SQL front end (inc1+inc2) — segment.ts (outer-jinja segmenter + length/newline-preserving, NO_OUTPUT_BUILTINS-aware placeholders), parse.ts (parseTemplated/tokenizeTemplated → one unified SQL ch0/1 + jinja ch2 "minijinja"-role Token[] over the untouched SQL lexers), parse-tag.ts (per-tag island lex/parse via grammars/minijinja/), tag-ast.ts (R2 ref/source/macro TagNodes with the quotes-excluded span contract), apply-tags.ts (R3 — {{ ref }}/{{ source }} in a FROM slot → a real TableSource.template), regions.ts (R4 — templateRegions/templateSymbols control-flow region tree + go-to-def symbols), variants.ts (templateVariants — arm-coverage branch enumeration). Total; reachable only through the barrel; the eight SQL grammars are untouched. minijinja is the oracle
src/scope/scope.ts         resolveScopes(query, dialect) — schema-free symbol table: visible sources, CTE resolution, output columns; the dialect string rides on Scope
src/qualify/               Schema (sqlglot-style mapping) + qualify — `*` expansion, unknown-table/column/field diagnostics, bottom-up column types
src/sema/resolve.ts        shared schema-aware column→source binder used by infer + lineage (local-first, then correlation to enclosing scopes)
src/infer/                 inferType — engine in infer.ts is dialect-agnostic; per-dialect knowledge in dialect.ts (Spark/T-SQL rules in functions.ts/literals.ts/types.ts, Snowflake's in snowflake.ts, coercion in coerce.ts)
src/lineage/               lineage/originsOf — base-table origins per output column; hops.ts (lineageAt/lineageOf → LineageHop) — the per-hop reference-spine DAG, a filtered view over the frozen scope/IR (cursor-anchored, shared hops fan out; the graph-factorable `Contribution` seam a future columnGraph reuses)
src/references/            referencesAt(scopes, offset, schema?, ast?) → Occurrences — the occurrence engine: declaration + every reference of the symbol under the cursor. Builds a reverse index on demand over the forward-only scope tree (object-identity within one tree, base-table Origin to unify across CTE/subquery when a schema is given). Backs LSP references/documentHighlight/codeLens (and later rename). Total: never throws; null off-symbol
src/symbols/               deriveSymbols — kind×modifier symbol model over the scope tree; carries types/origins when given a schema
src/document/              the living-document model — document.ts (SqlDocument: persistent, immutable, position-addressable per-file model; composes parse→resolveScopes with lazy schema analyze, caches it, holds tokens/cst/ast/scopes/diagnostics/lines, exposes tokenAt/nodeAt), line-index.ts (LineIndex: O(log n) position↔offset), node-at.ts (CST node at an offset; moved here from src/lsp)
src/completion/            scope-aware completion over a SqlDocument — own ATN candidate walk (atn-walk.ts) reimplementing antlr4-c3's algorithm with NO dependency, parser-factory.ts/config.ts, complete.ts (complete(); all eight dialects). Total: never throws
src/signature/             signature help — signatures.ts (curated per-dialect FUNCTION_SIGNATURES table ~20–40 fns/dialect, then a harvested doc-derived long tail in generated/*.ts — T-SQL 151, the others empty pending an offline syntax source), signature.ts (signatureAt(): full hints for curated/harvested fns, name + active-arg fallback for the rest). A pure token scan; total
src/api.ts                 uniform/layered/composable/immutable public surface: Dialect, parse(sql,dialect)→{ast,errors,diagnostics,cst,tokens}, analyze(sql,dialect,{schema?}), tokenize, the stateful SqlDocument front of the surface, complete/signatureAt, idempotent lift helpers (toAst/toScopes), composable qualify/lineage/deriveSymbols (accept string|IR|ScopeTree), referencesAt/Occurrences (the occurrence engine), typed result wrappers (TypeInfo.typeOf, Lineage.originsOf)
src/index.ts               public barrel: re-exports src/api.ts (incl. tokenize/Token/TokenRole, SqlDocument/LineIndex, complete/Completion, signatureAt/SignatureInfo, referencesAt/Occurrence/Occurrences, formatType, SyntaxDiagnostic) + the per-dialect parse*/lower building blocks (all eight dialects) and the raw shared passes
src/lsp/                   the LSP server (an application, not the library) — holds one SqlDocument per open file (rebuilt on edit) and serves every feature from it (features/*.ts): diagnostics (push + pull), hover, definition, references, documentHighlight, document-symbols, code-lens (reference counts), folding, selection, inlay-hints (output-column types), semantic-tokens (full+range+delta), completion + completion-resolve, signature. Imports ONLY the public surface (src/api.ts/src/index.ts) + vscode-languageserver-* + local presentation helpers — the seam to extract it into its own repo
tools/gen.mjs              generation driver (sorts .g4 so the lexer generates before the parser — tokenVocab)
```

Adding a dialect touches four places: `grammars/<dialect>/`, `src/<dialect>/parse.ts` + `lower.ts`, and one `InferDialect` entry in `src/infer/dialect.ts`. A missing function rule in a registry yields `unknown`, never a wrong type — that's the contract; don't guess return types.

**Public-API-only seam.** Everything under `src/` except `src/lsp/` imports only `antlr4ng` (completion is an owned ATN walk, NOT `antlr4-c3`). The LSP layer is the one editor consumer and reaches the rest of the codebase only through `src/api.ts`/`src/index.ts` (plus `vscode-languageserver-*`/`minimatch`) — so it can be lifted into its own repo without touching the library.

## Conventions

- One folder per dialect: `grammars/<dialect>/<Dialect>Lexer.g4` + `<Dialect>Parser.g4`. No `grammars/core/` — every dialect grammar is standalone.
- Generated TS (`src/generated/`) is **build output** — gitignored, regenerated by `npm run gen`. Never hand-edit it.
- Every dialect-specific grammar rule gets a comment linking the manual section that justifies it.
- The conformance corpus is the gate: a grammar change that regresses the corpus is **not done**. TDD for grammars = add corpus case → harness fails → edit grammar → harness green → commit.
- Match this file's decisions; if a decision turns out wrong, update this file in the same change that departs from it.
- **No descoping core work without Nicke's explicit clearance.** Cutting a real part of the job (e.g. expression modelling) out of scope is a decision only Nicke makes, stated out loud at the time. If something is too big to finish now, it stays a **visible Open Gap** that keeps answering "what's left" — never a quiet scope boundary, a "v1 doesn't do X", or an IR/code comment that removes it from view. Incomplete is fine; silent is not. **But visible is not done.** Building the easy 80% and filing the hard 20% as a tracked Open Gap is still a half-implementation — making the gap *visible* doesn't make the feature *finished*. An Open Gap is legitimate only for (a) genuinely separable work that is its own feature/subsystem (e.g. the type-inference engine), or (b) something needing a decision only Nicke can make — and it must be surfaced **before** building the easy half, so scope is agreed up front, not revealed after. "The harder half of what I'm building right now" is not a gap; it's unfinished work. Finish the feature's real cases — derived as well as base, the common collection/correlated forms — not just the convenient path. The only descoping Nicke has actually cleared is **transpilation**; **type inference** and **lineage** were never cleared (a prior edit wrongly listed them — corrected 2026-06-06) and are open, not Out. Everything else not yet built is an Open Gap, not an exclusion.
- **Drive to completion; do not checkpoint.** When you take on a piece of work (e.g. "type inference"), do it **full and complete** in one continuous push — every determinable case, **wired into its consumers**, working end-to-end. No "ifs, buts, or deferred." Building an engine (inference, symbols) and leaving it unwired is not done; "done" = a consumer can use it and it delivers the value, not that a layer compiles and its unit tests pass in isolation. Do NOT stop to report progress, summarise what's left, ask "should I continue?", or pause at each commit / TDD increment / gap — just keep building the next piece. The only legitimate stops: it genuinely works end-to-end, you are blocked on a decision only Nicke can make, or Nicke redirects. The only things that may stay unbuilt are the genuinely **undeterminable** (e.g. a type with no schema) — an inherent limit, not a deferral — recorded in PLAN.md, never used as a reason to stop early.
